## 1. 事前登録したパラメータ（検出数を見る前に固定）

**検出数を見てから動かさない。** 動かし始めると、検出数を見ながら形を作ることになる
（設計責任者の明示指示）。

**出典の有無を列に持つ。** 文献値は出典のとおり、裁量値は「文献に数値が無いことを
確認したうえで決めた」ことを明示する。あとから「これは根拠のある数字だったか」を
引けるようにするため。裁量値であること自体は問題ではない —— **裁量値を文献値のように
扱うことが問題**である。

| 記号 | 値 | 出典 | 何に使うか |
| --- | --- | --- | --- |
| **等値とみなす幅** | **±1.5%** | 文献値（LMW 2000） | 2 つ以上の極値が「同じ高さ」かの判定 |
| **ボックスの水平許容** | **±0.75%** | 文献値（LMW 2000） | 上辺・下辺それぞれの点が平均から離れてよい幅 |
| **ダブルボトムの最小間隔** | **22 営業日** | 文献値（LMW 2000） | 2 つの安値の距離。上限はウィンドウが兼ねる |
| **探索ウィンドウ** | **63 営業日** | 文献値（Savin-Weller-Zvingelis 2007。Bulkowski の H&S 平均完成期間に基づく） | 全極値がこの範囲に収まること。**全パターン共通** |
| **タッチ点数** | **3 + 2（最小 5）** | 文献値 | 回帰で 2 本の線を引くときの各辺の点数 |
| **フラッグ／ペナントの上限** | **15 営業日** | 文献値 | フラッグは未満、ペナントは以下 |
| **ε（水平とみなす傾き）** | **日次 0.1% 未満** | **裁量値**（文献に数値なしと確認済み） | 水平な上辺・下辺・平行の判定 |
| **旗竿** | **5 営業日以内に 10% 以上の上昇** | **裁量値**（同上） | フラッグ／ペナントの直前の急騰 |
| **トリプル／逆三尊の隣接間隔** | **10 営業日** | **裁量値**（同上） | 隣り合う谷どうしの距離。下限のみ |

**±0.75% は ±1.5% とは別の定数である。** ボックスの辺は「複数点が 1 本の水平線に
乗っている」ことを要求するので、2 点が等値かの判定より狭い。片方を他方から導かない。

**探索ウィンドウは全パターンで 63 営業日に統一する。** 保ち合い系だけ LMW の 38 日に
する案もあるが採らない —— **パターンごとにウィンドウを変えると、あとで「どのウィンドウが
効いたか」を切り分けられなくなる**（設計責任者の判断）。フラッグ・ペナントには 15 営業日の
別の上限があるので、63 日はそれより緩い外枠として働くだけである。

**±1.5% は ATR 連動にしない。** 銘柄のボラティリティで許容幅が変わると、同じ「ダブル
ボトム」が銘柄ごとに別の形を指すことになる。固定率で揃える（設計責任者の判断）。

### 感度分析はしない

**閾値を振って検出数の変化を記録し、ロバストな作動域を選ぶ、ということはしない。**
それは検出数を見ながら閾値を決めることであり、前のプロジェクトで撤退した構造そのもの
である（設計責任者の判断）。

文献（Savin et al.・Cervelló-Royo ほか）がやっているのは**研究としての頑健性検証**で、
ここでやろうとしているのは**運用値の決定**である。目的が違うので手法を借りない。

**閾値は固定したまま、検出数は記録だけする。** 動かすなら、動かす条件を先に決める。

これらを変えるときは §4 の質問ログを通し、**変更前に**決める。検出数を見たあとの変更は
「形を数字に合わせた」ことになるので、記録に残したうえで別物として扱う。

## 2. 対象パターン

**7 パターン。上昇ウェッジは対象外**（2026-09-08 決定）。

### 2.1 反転系（先に実装する）

極値は `swings.py` の**確定済み交互スイング**（`swings_as_of`）だけを使う。
安値と高値が交互に並ぶ列の、末尾側から必要な本数を取る。

#### 共通

| 項目 | 決め方 |
| --- | --- |
| ネックライン | **水平線**。2 点を結ぶ斜めの線は使わない（傾きを許すと許容傾きという新規パラメータが要る。ε を流用すると意味が変わる） |
| 完成 | **終値がネックラインを上抜けた日 T に成立**。極値が揃っただけでは成立させない |
| 確定ラグ | `swings.py` の k=3 だけ。**LMW の確定ラグ 3 本は使わない**（二重にかけると 6 本遅れる） |
| ウィンドウ | 使う極値がすべて T から遡って **63 営業日以内**に収まること（全パターン共通） |

#### R1 ダブルボトム

| | |
| --- | --- |
| 極値 | 安値 L1 → 高値 H → 安値 L2 |
| 等値 | `\|L1 − L2\| / ((L1 + L2) / 2) ≤ 0.015` |
| 間隔 | L1 と L2 が **22 営業日以上**離れる |
| ネックライン | 谷間の高値 H（1 点・水平） |
| 完成 | `終値[T] > H` |

#### R2 トリプルボトム

| | |
| --- | --- |
| 極値 | 安値 L1 → 高値 H1 → 安値 L2 → 高値 H2 → 安値 L3 |
| 等値 | 3 谷の平均 `m = (L1+L2+L3)/3` に対し、**各谷が m の ±1.5% 以内** |
| 間隔 | 隣接する谷（L1-L2・L2-L3）が**それぞれ 10 営業日以上**離れる |
| ネックライン | `max(H1, H2)`（谷間の高値 2 点のうち高いほう・水平） |
| 完成 | `終値[T] > max(H1, H2)` |

#### R3 逆三尊（逆ヘッドアンドショルダー）

| | |
| --- | --- |
| 極値 | 安値 E1（左肩）→ 高値 E2 → 安値 E3（頭）→ 高値 E4 → 安値 E5（右肩） |
| 肩 | E1 と E5 が両者の平均の **±1.5% 以内** |
| ネックライン点 | E2 と E4 が両者の平均の **±1.5% 以内** |
| 頭 | `E3 < E1` かつ `E3 < E5`。**深さの下限は設けない** |
| 間隔 | 隣接する谷（E1-E3・E3-E5）が**それぞれ 10 営業日以上**離れる |
| ネックライン | `max(E2, E4)`（水平） |
| 完成 | `終値[T] > max(E2, E4)` |

**R2 と R3 は別パターン**（D-2）。R2 は 3 谷が等値、R3 は中央が両側より低い。
E3 が 3 谷の平均 ±1.5% に収まりつつ E1・E5 の両方より低いことはありうるので、
**同じ 5 極値が両方に該当する形が出うる。その場合は両方を記録する**（どちらかに寄せない。
どちらの形として出やすいかは、検出数を見てから設計責任者が判断する）。

#### 「形は揃ったがネックライン未抜け」を数える

`detect_patterns(..., include_pending=True)` で、極値の並び・等値・間隔・ウィンドウを
すべて満たすが `終値[T] > ネックライン` だけを満たさない行も返す。`breakout` 列で
区別する。

**成立の定義は変えていない。** 既定では成立した行だけが返り、記録にも配信にも
未抜けの行は使わない。**成立が 0 件だったときに「条件が厳しい」のか「実装が間違って
いる」のかを 1 回で切り分けるためだけのもの**（設計責任者の指示）。

`cli pattern` は 4 つの数字を出す。

| 出す数 | 意味 |
| --- | --- |
| 成立 | ネックラインを上抜け済み |
| 形は揃ったが未抜け | 極値は揃っている。どこで落ちているかの切り分け用 |
| 形も揃わなかった銘柄 | 極値の並び・等値・間隔・ウィンドウのどれかで落ちた |
| 評価銘柄 | 履歴が足りて判定に入った銘柄 |

**成立・未抜けとも、銘柄コードと極値を日付つきで列挙する**（各30件まで、ネックラインに
近い順）。位置（バー番号）ではチャートで探せないので日付に直す。並び順は目視する順番を
決めるだけで、絞り込みでも閾値の判断材料でもない。

```
[pattern] --- 未抜け 11件（ネックラインに近い順）---
[pattern]   1392.T    inverse_hs     終値 2980.7 → ネックライン 3128.6 (+5.0%) / span 41本
[pattern]     谷 07-15 2830.0 / 08-11 2813.8 / 09-07 2870.1
[pattern]     山 07-29 3128.6 / 08-25 3113.5
```

これは **D-4 の「形を目視確認してから」を満たすための出力**である。成立 0 件が続く間も、
未抜けの形をチャートで見て「これをダブルボトムと呼んでよいか」を確かめられる。

読み方の目安（設計責任者の観点）:

- **0 件** → 未抜けの件数を見る。そこも 0 なら形の条件か実装、そこが出ていれば
  上抜け待ちなだけ
- **数百件** → ±1.5% が緩いか、スイング検出が細かい極値を拾いすぎている
- **数件〜数十件** → 想定内

### 2.2 保ち合い系

| # | パターン | 判定式 |

| C4 | 上昇ペナント | 旗竿あり、`上辺傾き < 0`・`下辺傾き > 0`（収束）、**15 営業日以下**、`終値 > 上辺` |

#### 実装上の読み（2026-09-10）

**判定式に書かれていなかった 5 点。** 新しい閾値は作っていない —— 既にある数値を
どこに当てるかの読み方だけを決めた。**読み方を変えると検出される形が変わる**ので、
納得できないものがあれば言ってほしい（`features/pattern.py` の docstring に同じものが
書いてある）。

| # | 決めたこと | なぜそう読んだか |
| --- | --- | --- |
| 1 | タッチ点は**確定済み交互スイングの末尾 5 極値**。交互なので必ず 3 + 2 に割れる | §2.1 が極値の出所を `swings_as_of` に固定している。他に極値の供給源が無い。「3 + 2（最小 5）」は 5 極値そのもの。**どちらの辺が 3 点かは形で決まる**（反転系と違い、末尾が高値で終わる形も採る） |
| 2 | 傾きは回帰直線の傾きを**その辺の平均値で割った日次の比率** | ε が「日次 0.1%」という**比率**で与えられている。価格/本のままでは比べられない |
| 3 | `終値 > 上辺` の上辺は**回帰直線を T まで延ばした値**。ただしボックスだけは上辺の平均 | ボックスの判定式は傾きではなく「平均からの距離」で水平さを要求しているので、上辺も平均で持つのが筋 |
| 4 | フラッグ／ペナントの営業日数は **`span`（最初の極値から T まで）** | 反転系の `span` と同じ数え方。パターンごとに数え方を変えない |
| 5 | 旗竿は「**最初の極値の終値 ÷ その 5 本前までの各終値 − 1**」の最大値 | 「直前の急騰」を「パターンが始まる時点までの上昇」と読んだ。T より後は見ない |

#### 重なりは寄せない（反転系との間でも）

**同じ極値が複数のパターンに該当したら全部返す。** §2.1 が R2 と R3 について決めた
方針を、保ち合い系にもそのまま広げた。

実際に重なる。**ボックスの ±0.75% は等値幅 ±1.5% より狭いので、谷 3 点で終わる
ボックスは必ずトリプルボトムにも該当する。** 上辺が水平なら上昇三角にも入る。
これは実装の取りこぼしではなく、判定式どうしの包含関係である。

**どの形として扱うかは、検出数を見てから設計責任者が決める**（§1 の「検出数を見て
から動かさない」は閾値の話で、重なりの扱いは別）。実装では寄せない。

#### C1 は傾きを制約し、散らばりを制約していない（2026-09-11 実測）

**`|上辺傾き| < ε` は「タッチ点が 1 本の水平線に乗っている」ことを要求していない。**
要求しているのは回帰直線の傾きだけである。

山が **2 点**なら回帰直線が必ず両点を通るので、この 2 つは同じことになる。
山が **3 点**になると別物になる —— **中央が大きく凹んだ V 字でも、両端が同じ高さなら
傾きは 0 に近い。**

2026-09-10 の実データ（成立 C1 11 件）:

| 銘柄 | 山 | 上辺傾き | 平均からの最大乖離 |
| --- | --- | --- | --- |
| 2331.T | 1241 → **1180.5** → 1227 | −0.044%/日（ε の半分以下） | **2.93%** |
| 1812.T | 5034 → **4892** → 5039 | −0.007%/日（ほぼ完全な水平） | **1.93%** |
| 9502.T | 3050 → **2968.5** → 2999 | −0.088%/日 | **1.47%** |

**山が 3 点の 3 件すべてがボックスの基準（±0.75%）を超えた。** 山 2 点の 8 件は
0.00〜0.45% で、形として妥当だった（設計責任者の目視・2026-09-11）。

**C2 には散らばりの条件がある**（各点が平均の ±0.75% 以内）。**C1 には無い。**
これは判定式の書かれ方の差であって、実装の取りこぼしではない。

**判定式は変えない。** C1 に散らばり条件を足すのは、検出数を見てから §2.2 の判定式を
変えることになる。ε も ±0.75% も動かさないと決めた以上、条件の追加も同じ扱いである
（§5 D-13）。**代わりに散らばりを測って表示する。** 判定で落とさず、見えるようにする。

#### C3・C4 が検出されない構造的な理由（2026-09-10 確定）

**日足かつ k=3 では、上昇フラッグと上昇ペナントは検出できない。** これは実装の不備でも
閾値が厳しすぎるのでもなく、**判定式と極値の出所の組み合わせから算術で決まる**。

極値を 5 点使い、5 点目が確定するのに k 本かかるので、

```
span = T − 1点目 ≥ (5点目 − 1点目) + k
```

`k=3` で `span ≤ 15`（ペナント）にするには **5 点が 12 本以内**、隣り合う極値の間隔が
**平均 3 本以下**。フラッグ（15 営業日**未満**）は**平均 2.25 本以下**になる。

k=3 のフラクタルは前後 3 本を見るので、間隔 2〜3 本の極値列は「**3 日ごとに天底が
入れ替わるノコギリ波**」である。**それは旗ではない。**

合成波では検出できる（テストで間隔 2 本の C3・間隔 3 本の C4 を固定してある）。
つまり**実装は動いており、実データにこの形が無いだけ**である。

**これを直さない**（§4 Q-2 の回答）。確定ラグをパターンごとに変えると極値の出所が
バラバラになり、15 営業日の数え方を変えると文献値を裁量で解釈し直すことになる。
**0 件という結果そのものが情報**なので、そのまま残す。

`cli pattern` の「未抜けの内訳」に C3・C4 が出ないのは、この理由による。

### 2.3 撤退・測定目標・比率

**判定には使わない。** 形の判定を通った行に付ける表示用の量で、条件でも閾値でもない。

| 量 | 決め方 |
| --- | --- |
| 撤退の目安 | **パターンの最安値**（逆三尊なら頭、ダブルボトムなら 2 安値の低いほう） |
| 高さ `h` | ネックライン − 最安値 |
| **測定目標** | **ネックライン + h**（文献上の目安。統計的裏付けは調べていない） |
| 抜け幅 | `終値 / ネックライン − 1`。負なら未抜け |
| `b` | 抜け幅 ÷ 高さ |
| **比率** | `(1 − b) / (1 + b)`。上（目標まで）÷ 下（撤退まで） |
| 損益分岐勝率 | `1 / (1 + 比率)` |

**測定目標は「文献上の目安」と明記して出す。** 押し目型で直近高値を目標にして
「目標が撤退より近い」問題が出たのと同じ轍を踏まないよう、**比率を必ず併記する**。

#### 比率は抜け幅で決まる

代数で決まる。抜けた直後（`b ≈ 0`）なら **比率 ≈ 1.0**、損益分岐勝率 50%。

| `b`（抜け幅÷高さ） | 比率 | 損益分岐勝率 |
| --- | --- | --- |
| 0.00 | 1.00 | 50.0% |
| 0.05 | 0.90 | 52.5% |
| 0.10 | 0.82 | 55.0% |
| 0.20 | 0.67 | 60.0% |

押し目型（直近高値を目標）の中央 0.38・損益分岐 72% とは別物である。

**比率は常に「T の終値で買ったら」の数字である。** 成立行では終値＝上抜け日の終値
なので実際の想定エントリーだが、**未抜け行では「まだ抜けていないのに今買ったら」の
仮定**になる。`b` が負になるぶん比率は 1 を大きく超える（2〜6 になることもある）。
**成立と未抜けの比率を同じ土俵で比べない。**

## 3. 記録

配信記録・結果付けの仕組みは `SCREENER.md` §3 のものをそのまま使う。

### 3.1 記録するのは成立だけ（2026-09-10 決定）

**`delivered_*.csv` に書くのは成立（ネックライン上抜け）した行だけ。監視（未抜け）は
表示のみで、記録しない。**

理由は**単位が違う**こと。

| | 成立 | 監視 |
| --- | --- | --- |
| 性質 | **事象**（抜けた日 1 日） | **状態**（同じ形が何日も続く） |
| 記録したら | 1 形 = 1 レコード | 1 形 = 滞留日数ぶんのレコード |

`outcome_*.csv` は T+1..T+5 の固定 5 本で、**事象にしか付けられない**。監視を記録すると
分母が「形の数」ではなく「形 × 継続日数」になり、**長く滞留した形ほど重く数えられる。**
反転系は滞留が長い（未抜けの形は数日〜数週間そのまま残る）ので、押し目型の連続点灯より
歪みが大きい。

### 3.2 監視の推移は日次スナップショットに残す

記録の単位を変えずに「監視に何日出ていたか」を後から引けるようにする。
`pattern_summary_<配信日>_asof<判定日>.json` に、その日の監視を残す。
**これは観測値であって台帳ではない**（上書きしてよい・結果付けの対象外）。

保全対象の `screen_summary_*.json`（19条件のもの）とは**別の prefix** にしてある。

**中身は 2 つに分かれる**（2026-09-11 実装時に決定）。

| キー | 中身 | 何のため |
| --- | --- | --- |
| `watch` | **全件**。銘柄・パターン・`breakout_pct`・連続日数だけ | 推移を追う。**連続日数もここから数える** |
| `watch_cards` | **カードに載せる上位 10 件だけ**。記録と同じ全列 | 配信は記録に書いてある値だけで描くため（§4.3） |

分けたのは**リポジトリを膨らませないため**。全件を全列で書くと 196 件で約 235KB/日、
年 60MB 近くになる。カードに要るのは上位 10 件だけである。

**監視の連続日数は (銘柄, パターン) 単位で数える。** カードが 1 行 1 パターンなので、
銘柄だけで数えると「C1 として 5 日目」と「C2 として 1 日目」に同じ数字が出てしまう。

### 3.3 列（2026-09-11 決定）

`delivered_<配信日>_asof<判定日>.csv` の 37 列。実体は
`screener/pattern_record.py` の `PATTERN_DELIVERED_COLS`。

| 群 | 列 |
| --- | --- |
| キー | `delivered_on` `asof` `ticker` |

`atr_t` は ATR14[T]。**MFE / MAE を ATR 単位で出すために持つ**（§3.4）。

**値はすべて T の引けまでで決まるものだけ。** 結果（T+1 以降）は

### 3.4 結果付け（2026-09-11 決定）

**押し目型（`resolver.py`）とは別の定義・別の列・別のファイル**にする。あちらは
押し安値 `lp` と直近高値 `h0_high` を参照していて、パターンにはその列が無い。
保全してある押し目型 15 件はあちらで付け続ける。

`pattern_outcome_<配信日>_asof<判定日>.csv`（実体は
`screener/pattern_resolver.py` の `PATTERN_OUTCOME_COLS`）。

| 列 | 中身 |
| --- | --- |
| `horizon_days` `n_bars` `censored` | 評価窓 **20 本**と実際に使えた本数 |
| `entry_open` `close_h` `ret_h` | Open[T+1] を基準にしたリターン |
| `max_high` `min_low` | 窓内の高安 |
| `broke_stop` `broke_stop_day` | 撤退の目安を割ったか（`Low < pattern_low`） |
| `reached_target` `reached_target_day` | 測定目標に届いたか（`High > target`） |
| `success` | **撤退を割る前に目標到達。同日なら失敗** |
| `mfe` `mae` `mfe_atr` `mae_atr` | エントリーからの最大上昇・下落幅（円と ATR 単位） |
| `up_pct` `down_pct` `rr` `breakeven_win_rate` | 配信時点の距離（記録の値。結果ではない） |

**MFE / MAE の基準はエントリー（Open[T+1]）**で、`ret_h` と揃えてある。ATR 単位に

**境界は厳密。** `Low < 撤退` と `High > 目標` で、同値では成立させない（押し目型と
同じ）。同じ日に両方起きたら順序が分からないので失敗側に倒す（`labels.py` と同じ）。

#### 最初の判断材料が揃うのは 10 月末以降

**20 本窓だと記録が確定するまで約 1 か月かかる。** 成立が 1 日 0〜13 件なら 20 件
貯まるのに 2〜3 週間、そこから結果が付くまでさらに 1 か月（設計責任者の見込み）。
急ぐ話ではないが、見込みとして持っておく。

### 6.1 構成

**パターン別にセクションを分ける**（2026-09-10 決定）。パターンごとに性格が違うので、
まずパターン別に見えるほうが読みやすい。

各パターンの中を **候補（成立）** と **監視（未抜け）** の 2 つに分ける。

| セクション | 中身 |
| --- | --- |
| 候補（成立） | ネックラインを抜けた銘柄。**全件出す。記録に残る**（§3.1） |
| 監視（未抜け） | 形は揃っている。**上値抵抗線に近い順で上位 10 件**。記録に残さない |

**監視は 10 件まで**（2026-09-11 決定）。1枚目のカードが縦に長くなりすぎない上限で、
押し目型で 9 件だったときの画像から見て 10 件前後が読める限界。196 件から絞る基準は
**上値抵抗線に近い順**＝「明日抜けるかもしれない順」で、緊急度であって優劣ではない。
**パターンごとに 10 件ずつではなく、全体で 10 件**（分けると 1 枚に収まらない）。

**成立 0 件の日も配信する**（2026-09-11 決定）。成立は 1 日 0〜13 件で振れるので、
0 件の日に何も送らないと**動いているのか壊れているのか分からない**。「本日の成立は
ありません」と明記したうえで監視だけを出す。

監視のほうが実用的でもある —— **抜けた日に買うなら前日に形を知っておくほうが早い。**
成立を見てから買うと既に抜けた後で、抜け幅が小さいほど比率が良いという §2.3 の
計算とも整合する。

**監視を出す理由**: 成立は 1 日 1 件あるかないかで、配信がほぼ毎日ゼロになる。
「形は揃った、あとは抜けるだけ」を前日に知っておけるほうが早い。

### 6.2 1枚目のカード（銘柄ごと）

### 6.4 同じ銘柄が複数セクションに出る

**パターン別にセクションを分けると、複数パターンに該当した銘柄が重複して見える。**
§2.2 のとおり判定式には包含関係があるので（谷 3 点のボックスは必ずトリプルボトム）、
これは例外ではなく**通常起きる**。実データ（2026-09-10・1,277 銘柄）で **15 銘柄**。

検出側で寄せない方針は変えない（§2.2）。**変えるとしたら配信側の見せ方だけ**である。

#### 想定外だった形: 成立と監視に分かれる（5202.T・2026-09-10）

当初は「同じ銘柄が候補セクションに 2 回出る」だけを想定していた。実データで
**それとは別の形**が出た。

| 銘柄 | パターン | ネックライン | 終値 | 状態 |
| --- | --- | --- | --- | --- |
| 5202.T | 逆三尊（R3） | 493.0 | 495.0 | **成立**（+0.4%） |
| 5202.T | 上昇三角（C1） | 495.9 | 495.0 | **未抜け**（−0.2%） |

**同じ銘柄・同じ日が「候補（成立）」と「監視（未抜け）」の両方に出る。** 極値は
同じで、ネックラインの引き方（水平な `max(E2,E4)` か、上辺の回帰直線か）が 2.9 円
違うだけで、抜けたか抜けていないかが分かれた。

カードに「複数パターン該当」と書くだけでは読めない —— **「抜けた」と「抜けるのを
待つ」が同時に立つ**ことになる。

#### 方針（2026-09-11・設計責任者）

**配信では成立を優先し、同一銘柄が成立していれば監視から外す。** 既に抜けている
銘柄を「抜けるのを待つ」セクションに出すのは読み手を混乱させる。

**記録には影響しない。** 記録は成立のみ（§3.1）なので、監視から外すのは表示だけの
話である。検出側（`detect_patterns`）も変えない —— 両方返したまま、配信側で落とす。

実装は配信を作るときに行う。`cli pattern` は「同じ銘柄で複数パターンに該当: N 銘柄」を
毎回出しているので、重なりの量は配信を作る前に分かる。
