## 0. この文書の位置づけ

**これは検証プロジェクトではなく運用ツールである。** 毎営業日、条件に合った銘柄を
LINE に配信し、配信の実績を貯める。それだけを行う。

`docs/DESIGN.md`（詳細設計）・`docs/TASKS.md`（作業分割）は 2026-08-30 に終了した
別プロジェクト（v8 順張り押し目・検証）のものであり、`docs/CLOSING.md` に終了記録が
ある。**この文書はそれらを引き継がない。**

引き継がないものを明示する（同じ docs に置くため、読み違いを避ける）:

| 引き継がないもの | 理由 |
| --- | --- |
| 事前登録済みの検定数（DESIGN.md §10.6 の 174 検定） | 検定をしないので数えるものが無い |
| 停止規則・撤退基準（DESIGN.md §10.3） | 撤退の判断をする対象が無い |
| ホールドアウト（2026-02〜2026-08）の未使用状態 | このツールは検定に使わないので消費しない。CLOSING.md の「残っている資産」のまま |
| t 値・p 値・IC・超過リターンの検定 | 出さない。§3.4 で出すのは件数と実績の表だけ |
| スコア（V1〜V3 / W1〜W3）・F 除外・プール百分位 | §2 のとおり使わない |

逆に引き継ぐのは**コードだけ**である（§4）。DESIGN.md を参照する箇所は、
「その式の実装がそこにある」という意味であって、そこの検証結果を根拠にしていない。

**DESIGN.md と TASKS.md は終了済みとして編集しない。** この文書に書いたことが
このツールの正の情報源であり、両者が食い違ったらこの文書を正とする。

## 1. 目的と範囲

- 入力: `data/store` の日足（`data-daily` ワークフローが毎営業日更新している）
- 判定: 銘柄ごとに §2 の条件をブール判定する。全て満たしたものが配信候補
- 出力: LINE への画像配信（既存経路をそのまま使う）と、配信記録（§3）
- 判定日 T の引けまでの情報だけで決め、T+1 朝に配信する。行動は T+1 以降

範囲外: 発注、建玉管理、損益計算、銘柄の優劣付け。並び順に意味を持たせない。

## 2. 条件（19 条件）

全 19 条件の **AND** で候補にする。注記扱いの条件は無い。順位もスコアも作らない。

押し目状態（形成中 / 反発開始 / ブレイク）による限定は**しない**。C 群・D 群が実質的に
状態を規定するため、状態で重ねると二重になる。実際、D1 ∧ D2 は反発トリガー trig_a
（DESIGN.md §4.3）と同じ式であり、C4 は「H0 を未更新」＝ 完了状態の除外にあたる。

### 2.1 A 群（ユニバース）

| ID | 条件 | 使う量 |
| --- | --- | --- |
| A1 | 20日平均売買代金 ≥ 3億円 | mean(Close×Volume, T−19..T)。`universe.build.liquidity_stats` と同じ式 |
| A2 | 終値 ≥ 300円 | Close[T] |
| A3 | 履歴 ≥ 250営業日 | T までの本数 |
| A4 | 5営業日以内に決算発表なし | `jpx_lists.next_earnings_business_days` > 5 |

A 群は 19 条件に数える。実装では前段のユニバース（`universe/build.py`）を母集団に
使うが、A1〜A3 は銘柄の系列から T 基準で判定し直す（ユニバースの閾値は 2億円 / 200円
で A 群より緩いので、母集団としては A 群の上位集合になる）。

**ユニバースが追加で課している条件**（19 条件には無いが、母集団の時点で効いている）:
株式のみ（ETF・ETN・REIT・インフラファンド・優先株を除外）、最終足が 7 日以内、
未記録分割の疑いなし。SPEC.md §1 の決定事項をそのまま使っている。

### 2.2 B 群（トレンド）

| ID | 条件 | 使う量 |
| --- | --- | --- |
| B1 | SMA75 > SMA200 | `indicators.sma` |
| B2 | SMA200[T] > SMA200[T−20] | 傾きの参照は 20 営業日（DESIGN.md G1 の 30 とは別の値） |
| B3 | 終値 ≥ SMA200 | |
| B4 | 終値 ≥ 過去252日の最高値 × 0.75 | max(High[T−251..T]) |

### 2.3 C 群（押し目の形）

| ID | 条件 | 使う量 |
| --- | --- | --- |
| C1 | 0.03 ≤ depth_pct ≤ 0.08 | `pullback.pullback_state` の `depth_pct` |
| C2 | Lp > L0.low | `lp_value` > `l0_low` |
| C3 | 2 ≤ duration ≤ 12 | `d`（押し目日数） |
| C4 | max(High[h0+1..T]) < H0.high | H0 を未更新 |

### 2.4 D 群（反発）

| ID | 条件 | 使う量 |
| --- | --- | --- |
| D1 | 終値 > SMA5 | |
| D2 | 終値 > High[T−1] | |
| D3 | position ≥ 0.50 | `pullback_state` の `position` |
| D4 | d3_ma_dist ≤ 1.0 かつ landing_ma ∈ {SMA5, SMA25, SMA75} | `dimensions.landing_ma` |

D4 の tie-break（距離が同じ線が複数あるとき）は `landing_ma` の既存の順序
（`LANDING_MA_NAMES` = 短い線が先）をそのまま使う。ここを変えると配信記録と
特徴量表（d3_ma_dist）がずれるため、**変更しない**。200 日線で止まったものは
候補にしない（D4 の許容線に SMA200 を入れない）。

### 2.5 E 群（除外）

| ID | 条件 | 使う量 |
| --- | --- | --- |
| E1 | d2_rs60 が当日候補内の上位10%でない | rs60 = ln(C[T]/C[T−60]) − ln(IDX[T]/IDX[T−60]) |
| E2 | d3_dev5 ≤ 0.02 | `pullback_state` の `dev5` |
| E3 | T − lp ≤ 5 | 押し安値からの経過本数 |

**E1 だけがその日の候補集合に依存する。** 手順を固定する:

1. A〜D と E2・E3 を銘柄ごとに判定する（18 条件。銘柄ごとに閉じている）
2. 18 条件を全て満たした集合を **E1 の母集団** とする
3. 母集団が **10 件未満の日は E1 をスキップ**し（全て成立扱い）、配信記録の
   `e1_skipped` を立てる
4. 10 件以上なら、母集団内の rs60 の 90 パーセンタイルを閾値とし、
   `rs60 ≤ 閾値` を満たすものだけ通す

母集団の外の銘柄では E1 は**未判定**（欠損）のままにする。18 条件のどれかで落ちた
銘柄を「E1 で落ちた」と記録しないため。

これは直近 20 営業日プール（DESIGN.md §6.3）の百分位ではなく、**その日の候補集合の中の
相対位置**である。§2.7 が禁じているのは前者であり、E1 は後者として明示的に許可する。

E1 が母集団不足で常時スキップになる場合の扱いは、**数字を見る前に §7 D-1 で固定してある。**

### 2.6 欠損時の扱い

**全条件、欠損は不成立**（候補から外す）。判定できないものは配信しない。
検証（DESIGN.md §6.1）は欠損を通過扱いにしていたが、運用では逆にする。

押し目構造が無い銘柄（H0 / L0 / Lp が定義できない）は C 群・D3・D4・E2・E3 が
そろって欠損になるので、この規則だけで自然に落ちる。

**唯一の例外は A4。** 決算発表予定日が取れない場合（JPX のローリング更新の外、
または当該銘柄の予定が無い）は成立扱いにし、`a4_earnings_unknown` を立てて
カードに「決算日未取得」と明記する。取れないだけで全部落ちると候補がゼロになるため。

**A4 は多くの日で実質的に効かない（2026-08-31 の実測）。** その日のユニバース通過
1,323 銘柄のうち、判定日以降の決算発表予定日が取れたのは **37 銘柄（2.8%）** だけで、
残る 1,286 銘柄（97.2%）は `a4_earnings_unknown` になった。JPX が公開するのは
「直近に決算期末を迎えた会社」の予定日だけで、8 月末は第1四半期の発表がほぼ終わり
次の波（10〜11 月）がまだ公開されていない端境期にあたるため（`docs/DATA_SOURCES.md` §1）。
カバー率は決算期に高く、期の谷間で 0 に近づくという季節性を持つ。取得経路の不具合では
ない（`references` は毎営業日 3,213 件を取得できている）。この性質を前提に、
カードの「決算日未取得」表示を省略しない。

### 2.7 条件に使ってはいけないもの

- **スコア計算をしない。** 総合スコア・次元スコア・重み付き合成を作らない。
  候補は「19 条件を全て満たしたか」の 1 つのブール値だけで決まる
- **F 除外を使わない。** DESIGN.md §6.1 の F1〜F14 は持ち込まない
- **直近 20 営業日プールの百分位を使わない**（DESIGN.md §6.3）。閾値は絶対値で書く。
  唯一の例外が E1 で、そこも「その日の候補集合の中の順位」であって過去日プールではない
- 順位を付けない

### 2.8 出力

- **所属業種の 5 日順位（昇順）→ 20 日平均売買代金（降順）**に並べる（2026-09-05 変更、§2.9）。
  順位表が無い日は売買代金の降順だけ
- **並び順は優劣ではない。** 業種の 5 日リターンで先に並べるが、その順が成績に効くという
  裏付けは無い（§2.9）
- 同一 33 業種は **3 件まで**（その業種の中で売買代金の上位から詰める）
- 業種順位・売買代金が同値のときは銘柄コード順（実行のたびに並びが変わらないようにするため）
- 業種が取れない銘柄は上限の対象外（互いに別業種として扱う）。業種順位も付かないので末尾に置く
- 件数の上限は置いていない

### 2.9 業種の強弱（並び順にだけ使う）

ユニバース通過銘柄の**等加重リターン**を業種ごとに **5 日・20 日**の 2 本で毎営業日計算し、
**5 日リターンの降順に 1 位から**順位を付ける（`features/sector.py`）。

**この順位は並び順にだけ使う。条件にも除外にも使わない。**

- 19 条件と閾値は変えていない
- **候補の集合は変わらない。** 上限は業種ごとの件数なので、同じ業種の中で売買代金の
  上位から選ばれる点が並べ替えの前後で変わらない（`tests/test_sector.py` で固定）
- §2.2 の「スコアを作らない」に抵触しない —— 銘柄に点数を付けているのではなく、
  業種を並べているだけで、判定は 19 条件のブール判定のまま

計算:

| 項目 | 決め方 |
| --- | --- |
| リターン | `Close[T] / Close[T−look] − 1`。**T の引けまでしか読まない** |
| 窓 | 順位付けは 5 日。20 日は併記するだけ（指定された値であり、探索して決めたものではない） |
| 加重 | 等加重。時価総額も浮動株数も取得していないので、根拠のある加重を装わない |
| 構成銘柄 | **ユニバース通過分のみ**（下の測定を参照） |
| T の足が無い銘柄 | その業種の計算から外す（前日の値で代用しない） |
| 同率 | 業種名の昇順で固定 |

#### 構成銘柄をユニバース通過分にした根拠（2026-09-05 測定）

2026-09-03 時点で通過 1,327 銘柄、33 業種すべてが現れる。ただし規模の差が大きい。

| 業種数 | 銘柄数 |
| --- | --- |
| 最小 | 2（空運業）。石油・石炭製品 3、水産・農林業 4、鉱業 5 |
| 中央 | 21 |
| 最大 | 143（情報・通信業） |

10 銘柄未満が 9 業種ある。**小さい業種ほど順位は振れる**が、差は思ったより小さい。
committed の日次スナップショット 08-17〜09-03 で 5 日順位の日次変動を測ると:

| 母集団 | 平均 \|Δ順位\|（1日あたり） |
| --- | --- |
| 10 銘柄未満（9 業種） | 7.7 |
| 30 銘柄以上（16 業種） | 5.7 |

1 銘柄抜いたときの順位変化（leave-one-out・最大）は鉱業（5 銘柄）で 8 位ぶん動くが、
医薬品（32 銘柄）でも 5 位、その他金融業（19 銘柄）で 6 位動く。

**読み方: この順位は業種の大小によらず振れる。** 小さい業種だけの問題ではなく、
33 業種を 5 日等加重リターンで並べること自体がその程度の解像度しかない。
だから順位は**並び順にだけ**使い、除外には使わない。免責の「優劣ではありません」は
この測定に裏打ちされている。

全上場に広げない理由: 流動性の低い銘柄の終値は飛びやすく、別種のノイズが入る。
候補はそもそも通過集合から出るので、関係する母集団はこちらである。

**最低構成銘柄数の閾値は置かない。** 置くなら新しいパラメータになるので §7 の質問ログを
通す（CLAUDE.md）。代わりに順位表に `n`（構成銘柄数）を必ず残し、読み手が割り引けるようにする。

## 3. 記録（この節は実装済み）

### 3.1 なぜ条件より先に入れるか

線ごとの勝率を後から出したくなったとき、記録が無ければ何も言えない。配信のたびに
1 行ずつ貯まる仕組みは、あとから足すより先に入れておくほうが安い。数十件貯まった
時点で §3.4 の表が出る。

記録は 2 つのファイルに分ける。**配信記録は書き換えない。**

```
data/daily/delivered_YYYY-MM-DD.csv   配信した銘柄（配信日に書く。以後不変）
data/daily/outcome_YYYY-MM-DD.csv     その 5 営業日後の結果（あとから付く）
```

`YYYY-MM-DD` はどちらも**配信日**で、1 対 1 に対応する。判定日 T は `asof` 列に持つ。
日付別ファイルにするのは、日次で肥大するファイルを毎回丸ごとコミットしないため
（CLAUDE.md「よくある落とし穴」）。件数が少ないので圧縮しない（git の差分で読める）。
どちらも `data/daily/` なので、既存の `data-daily` ワークフローがそのままコミットする。

### 3.2 配信記録 `delivered_<配信日>_asof<判定日>.csv`

1 行 1 銘柄。**T の引けまでのデータだけで作る。**

| 列 | 内容 |
| --- | --- |
| `delivered_on` | 配信日（LINE に流した日） |
| `asof` | 判定日 T。この日の引けまでの情報だけで決めた |
| `ticker` / `name` | 銘柄コード・銘柄名（取れなければ空） |
| `landing_ma` | **止まった線**。`SMA5` / `SMA25` / `SMA75` / `SMA200` のいずれか |
| `landing_ma_value` | 押し安値の日のその線の値 |
| `landing_dist_atr` | \|押し安値 − その線\| / ATR14[T] |
| `lp` / `lp_date` | **押し安値** Lp とその日付 |
| `h0_high` / `h0_date` | **直近高値** H0.high とその日付 |
| `close_t` | T の終値 |
| `atr_t` | ATR14[T] |
| `state` | 押し目状態（形成中 / 反発開始 / ブレイク） |
| `depth_pct` | 押しの深さ |
| `pullback_days` | 押し目日数 d |
| `adv_jpy` | 20日平均売買代金（並び順の根拠、§2.8） |
| `sector33` | 33業種（同一業種3件までの根拠、§2.8） |
| `a4_earnings_unknown` | True ならカードに「決算日未取得」と出す（§2.6） |
| `e1_skipped` | True ならその日は母集団不足で E1 を適用していない（§2.5） |
| `earnings_days` | 決算発表までの営業日数（取れなければ空） |
| `streak` | **連続点灯日数**。今日が初日なら 1 |
| `prev_delivered_on` | 前回この銘柄が候補になった配信日（無ければ空） |
| `sector_rank_5d` / `sector_rank_20d` | 所属業種の 5 日・20 日リターン順位（1 が最強。§2.9） |
| `sector_ret_5d` / `sector_ret_20d` | 所属業種の 5 日・20 日等加重リターン |

**「止まった線」の決め方**: 押し安値 Lp に最も近い移動平均線（5/25/75/200 の 4 本）。
DESIGN.md §5 の `d3_ma_dist`（Lp に最も近い SMA との距離 /ATR）と同じ判定で、距離
だけでなく線の名前も返すようにした（`features/dimensions.py` の `landing_ma()`）。
特徴量表と配信記録が同じ関数を通るので、両者がずれない。

距離も一緒に記録するのは、最も近い線が遠い場合（例えば 3 ATR 先）に「その線で
止まった」とは言いにくいためで、集計時に `landing_dist_atr` で絞れるようにしてある
（§3.4）。線を絞る閾値は決めていない。記録側では捨てない。

#### ファイル名に判定日を入れる（2026-09-04 決定）

`delivered_2026-09-04_asof2026-09-03.csv` のように、**配信日と判定日 T の両方**を
ファイル名に持つ。`screen_summary_*.json` と `outcome_*.csv` も同じ形にする。

同じ JST の日に 2 回走ると判定日が変わる。引け前（7:00 JST の定期実行）は T = 前営業日、
引け後（手動実行）は T = 当日になる。配信日だけの名前だと、この 2 つが同じファイルを
取り合う。**2026-09-03 に実際に起きた**: 朝の 0 件が `delivered_2026-09-03.csv` に残り、
引け後に判定した 5 件は保存されなかった。要約 `screen_summary_*.json` は逆に上書きする
規則だったため、朝の台帳（0 件）と引け後の要約（母集団 5 件）が組み合わさって、
存在しない日が配信された。

判定ごとに別ファイルにすれば両方残る。上書き規則をどちらかに揃える案は採らない ——
朝を残せば引け後の判定が消え、引け後を残せば台帳が書き換わる。どちらも情報が減る。

同じ配信日・**同じ判定日**のファイルが既にある場合は上書きしない。その日に何を出したかの
台帳であり、あとから作り直さない。同じ判定日での再実行は同じ結果になるので、これで失う
ものは無い。

**書かなかったときは呼び出し側に返す。** `save_delivered` は `(パス, 書いたか)` を返し、
`step_screen` は書けなかった場合に「保存した」と書かず警告を出す。要約にも
`delivered_written` を残し、配信本文と画像カードに注記を出す。以前は Path だけを
返していたため、ログには「5 件を保存」と出ているのにファイルは 0 件のまま、という
状態が誰にも見えなかった。

#### 旧名の扱い（移行）

リポジトリにある 6 ファイル（09-01 / 09-03 / 09-04 の delivered と screen_summary）は
**リネームで移行した**。判定日は各ファイルの `asof` から取れるので機械的に決まる。
例外は 0 件だった `delivered_2026-09-03.csv` で、中身に `asof` の行が無いため、
run #36 のログ（`判定 2026-09-02 の引け`）から `asof2026-09-02` とした。

読み込み側は**旧名も受け付ける**。判定日が名前に無い場合は中身の `asof` から補う。
古い成果物やロールバックした版が混ざっても黙って消えないようにするための安全網で、
新しく書くファイルは常に新名になる。

#### 2026-09-03 引け時点の 5 件は回収済み（作り直さない）

引け後の run #37 が保存できなかった判定は、**翌朝の定期実行 run #38 が同じ判定日で
記録している**。7:00 JST の実行は引け前なので T = 前営業日、つまり 09-03 になるため。
`delivered_2026-09-04_asof2026-09-03.csv` の 5 件がそれで、要約も
`screen_summary_2026-09-03_asof2026-09-03.json` と全項目一致する
（`n_evaluated` 1327 / `n_pool` 5 / `n_candidates` 5 / `fail_counts` 18 項目 /
`landing_ma_candidates` SMA5:3・SMA25:2 / 地合い 強(6/6) / `earnings_known` 33）。

**同じ判定を `delivered_2026-09-03_asof2026-09-03.csv` として作り直すことはしない。**
同じ判定日の記録が 2 つになり、§3.3 の結果付けで同じ 5 銘柄が二重に数えられる。
また 09-04 の記録は `streak` = 1・`prev_delivered_on` = 空で確定しており、あとから
09-03 の記録を足すとその 2 列と整合しなくなる（§3.2「台帳は後から作り直さない」）。
Actions キャッシュから store を復元して再実行する必要も無い。

失われたまま戻らないのは、引け前 run #36 の要約（`asof2026-09-02`）だけである。
上書きされて消えた。ログには残っているが、手で書き戻すと観測値と区別が付かなくなるので
作らない。台帳側の `delivered_2026-09-03_asof2026-09-02.csv`（0 件）は残っている。

**同じ銘柄が複数日にわたって候補になることがある**（押し安値を割らない限り条件は生き続ける）。
これは仕様どおりで、記録上は日ごとに別レコードになる。後から数えるときのために、
記録時点で次を確定させておく。

- `streak` … 直前の配信日から連続で候補に出ている日数（今日を含む）
- `prev_delivered_on` … 今日より前で最後に候補になった配信日。間が空いた「断続点灯」も追える
- `h0_date` … 押し目の起点。**同じ押し目エピソードかどうかはこれが一致するかで判定する**
  （連続していても `h0_date` が変わっていれば別の押し目）

これらは配信記録から後から導くこともできるが（`ticker` と `h0_date` と `delivered_on` を
突き合わせればよい）、記録時点で書いておく。あとから遡ると、ワークフローが失敗して
配信記録のファイルが欠けた日を「候補が出なかった日」と区別できないため。
逆に `streak` はファイルが欠けた日をまたぐと実際より短くなる。記録した時点で分かることを
そのまま書く方針で、あとから直さない。

**連続点灯の 2 日目を 1 トレードと数えるか 2 トレードと数えるかは決めていない。**
記録を取るところまでが今の範囲で、数え方は記録が貯まってから決める（§8 D-2）。

### 3.3 結果 `outcome_<配信日>_asof<判定日>.csv`

評価窓は **T+1 から T+5 の 5 営業日固定**。エントリーの基準は T+1 の寄付き
（SPEC.md §1 と同じ）。

| 列 | 内容 |
| --- | --- |
| `delivered_on` / `asof` / `ticker` | 配信記録と同じキー |
| `resolved_on` | 結果を付けた日 |
| `horizon_days` / `n_bars` / `censored` | 窓の本数（5）／実際に使えた本数／打ち切りか |
| `entry_open` | Open[T+1] |
| `close_h` | **5 日後の終値** Close[T+5]（打ち切り時は取れた最後の終値） |
| `max_high` / `min_low` | **期間中の最高値・最安値** |
| `ret_h` | `close_h / entry_open − 1` |
| `broke_lp` / `broke_lp_day` | **押し安値を割ったか**（Low < Lp）と、割った最初の日 |
| `reached_h0` / `reached_h0_day` | 直近高値を更新したか（High > H0.high）と、その最初の日 |
| `recovered_sma5` / `recovered_sma5_day` | **5 日線を回復したか**（Close > SMA5）と、その最初の日 |
| `success` | 押し安値を割る前に直近高値を更新したか（SPEC.md §1 の成功の定義） |

日付は T からの本数（T+1 が 1 日目）。

- **窓は固定する。** 5 本目が出た時点で確定させ、以後は足が伸びても作り直さない。
  結果ファイルが既にある配信日には触らない
- **5 営業日の数え方**は市場の営業日軸（`store` の指数、無ければ全銘柄の日付の
  和集合）。祝日表を持たない、データ駆動の判定
- **打ち切り**: 市場側で 5 営業日が経過したのに銘柄側の足が 5 本に満たない場合
  （売買停止・上場廃止）は、取れた分だけで確定させて `censored` を立てる。記録ごと
  落とすと生き残った銘柄だけが残り、実績が良く出る方向に偏る
- `success` は、同じ日に高値更新と押し安値割れが両方起きた場合は失敗に倒す
  （順序が分からないため。`validation/labels.py` と同じ扱い）

### 3.4 集計

`summarize_by_landing_ma()` が、止まった線ごとに次の表を出す。

| 列 | 内容 |
| --- | --- |
| `landing_ma` | 止まった線 |
| `n` / `n_resolved` | 配信件数 / 結果が付いた件数 |
| `success_rate` | `success` の割合 |
| `broke_lp_rate` | 押し安値を割った割合 |
| `recovered_sma5_rate` | 5 日線を回復した割合 |
| `mean_ret_h` | `ret_h` の平均 |

`max_dist_atr` を渡すと、押し安値がその距離より遠い記録を除いて集計する。

### n=0 の行を落とさない

**SMA5 / SMA25 / SMA75 / SMA200 の 4 行は常に出す。** 候補に一度も出ていない線は
`n=0` の行になる。

**記録がある状態での `n=0` は「D4 がその線を通していない」という情報であって、
データ不足ではない。** D4 は `d3_ma_dist ≤ 1.0` かつ `landing_ma ∈ {SMA5, SMA25, SMA75}`
なので、押し目が 200 日線で止まった銘柄は距離に関わらず全て落ちるし、75 日線で止まっても
1 ATR より遠ければ落ちる。§3.6 の `landing_ma_all`（D4 適用前）と並べると、その線で
止まった銘柄が毎日どれだけあって、そのうち何件が D4 を通ったかが読める。

2026-09-01・09-02 の実測では、D4 適用前に SMA75 が 219〜221 件／SMA200 が 250〜252 件
あるのに対し、候補に出たのは SMA5 と SMA25 だけだった。この対比が D4 の効き方そのもの
である。

素朴に `groupby` で集計すると、候補に出ていない線は**行ごと表から消える**。読み手には
「まだ集計されていない」のか「候補に出ていない」のかが区別できない。数か月後に表を見る人
（次のセッションを含む）が行の不在から意味を読み取ることはできないので、行を残す。

`n=0` の行の各率は 0.0 ではなく**欠損**にする（0 勝ではなく未出走なので）。
台帳そのものが空なら 4 行とも `n=0` になるが、それは「まだ記録が無い」だけで
D4 の情報ではない。止まった線が取れなかった記録がある場合だけ、末尾に「（線なし）」を足す。

**表を出すところまでがこのツールの仕事である。** 件数が十分か、どの線を採るか、
条件を変えるかの判断はしない（CLAUDE.md「検証結果を解釈しない」）。

### 3.5 時点整合（未来参照の禁止）

CLAUDE.md の絶対規則をこのツールにも適用する。

- `screener/record.py` は T の引けまでしか読まない。T より後の足が系列に付いていても
  記録は同じになる（テストで確認）
- `screener/resolver.py` だけが T+1 以降を読む（`validation/labels.py` と同じ立場）。
  逆に T 以前の値は計算し直さない —— 押し安値・直近高値・止まった線は配信記録に
  書いてある値をそのまま使う。これで「記録した時点の判断」と「その後の結果」が
  混ざらない
- 窓が固定なので、あとから足が伸びても確定済みの結果は変わらない（再計算一致、
  DESIGN.md §11 と同じ考え方をこのツールにも適用する）

### 3.6 監視（条件を動かすためではなく、動いているか見るため）

`screen` は毎営業日、次をログに出し、同じ内容を
`data/daily/screen_summary_<配信日>_asof<判定日>.json` に残す。

| 項目 | 何が分かるか |
| --- | --- |
| `n_evaluated` / `n_pool` / `n_candidates` | 評価件数 / 18条件通過（E1 の母集団） / 候補件数 |
| `e1_skipped` / `e1_threshold` | E1 を適用したか、したときの rs60 の閾値 |

**なぜリポジトリにも残すか**: Actions のログは 90 日で消える。E1 のスキップ率も
線ごとの分布も数週間から数か月かけて見るものなので、ログだけでは足りない。
配信記録（`delivered_*.csv`）と違ってこのファイルは上書きしてよい —— 判断の記録ではなく、

`sector_candidates` と `adv_candidates` も同じ立場で、**集計するだけ**である。
2026-09-04 は候補 5 件中 3 件が銀行業、売買代金は最大 190 億円・最小 3.6 億円で
1 桁以上開いていた。記録が貯まったときの見直し候補ではあるが、いま条件は凍結中

## 4. LINE 配信

毎営業日、その日の配信記録をそのまま LINE に流す。**判定も整形もここではやり直さない。**

### 4.1 経路

既存の Cloudflare Worker（`src/worker.js`）の `POST /`（JSON `{"text": ...}`）で
テキストを push する。**Worker・`wrangler.toml`・Secrets 名は変更しない**
（CLAUDE.md「LINE 経路を変えない」）。

| 環境変数 | 用途 |
| --- | --- |
| `WORKER_URL` | Worker のエンドポイント。未設定なら本文を作るだけで送信しない |
| `WORKER_AUTH_TOKEN` | 任意。Worker 側で `UPLOAD_TOKEN` を設定している場合に必要 |
| `CHROMIUM_PATH` | 任意。Playwright の既定リビジョンと環境の Chromium がずれる場合の明示パス |

Worker の口は 2 つ。`POST /`（JSON `{"text": ...}`）でテキスト、`POST /upload`
（multipart `{file, caption?}`）で画像を 1 枚。**1 リクエストにつき画像 1 枚**なので、
2 枚組は 2 回投げる。

**通常の配信は画像2枚だけ。テキストは送らない（2026-09-04 決定）。**
`/upload` に `caption` を付けると、Worker は画像とは**別に**テキストを 1 通 push する
（`src/worker.js`: `if (caption) messages.push({type:"text", ...})`）。本文をキャプション
として渡していたため、2026-09-04 の配信は本文 1 通 + 画像 2 通の計 3 通になっていた。
`caption` は付けない。Worker 側は変更しない（CLAUDE.md「LINE 経路を変えない」）。

**配信は画像カード2枚（§4.5）。** SPEC.md §5 のインフォグラフィック（Jinja2 +
Playwright で HTML → PNG）を新規に実装した。TASKS.md の M3b・M5 は L1 不通過により
「実施せず」で終わっており流用できる描画コードは無かったので、描画層はゼロから作った。

**描画または送信に失敗した日だけテキスト push に落ちる（§4.4）。** Chromium が無い・
フォントが無い・起動に失敗する、のいずれでも配信そのものは止めない。

### 4.2 本文

見出し:

- 日付（配信日と判定日 T）
- 地合いゲージ（DESIGN.md §8.1 の6点。**順位にも条件にも使わない。表示だけ**）
- その日の候補件数
- E1 がスキップされた日はその旨を1行（§2.5）
- 並びが売買代金の降順であり順位ではないこと（§2.8）

カード（1銘柄1枚、配信記録の順）:

| 項目 | 記録の列 |
| --- | --- |
| 銘柄コード・銘柄名 | `ticker` / `name` |
| 終値 | `close_t` |
| 状態 | `state` |
| 20日平均売買代金 | `adv_jpy` |
| 止まった線と距離 | `landing_ma` / `landing_dist_atr` |
| **撤退ライン**（押し安値） | `lp` |
| **目標の目安**（直近高値） | `h0_high` |
| 深さ・押し目日数 | `depth_pct` / `pullback_days` |
| 決算までの日数 | `earnings_days`。取れていなければ**「決算日未取得」と明記**（§2.6） |
| 連続点灯日数 | `streak`。2 日目以降だけ「（連続N日目）」と出す |

押し安値と直近高値には「撤退ライン」「目標の目安」という語を添えるが、**株数も損益も
出さない**（SPEC.md §5「価格・株数・損益の計算は載せない」）。

**候補0件の日も配信する。** その日は「19条件を全て満たす銘柄がありませんでした」と、
落ちた条件の上位3つを条件 ID・ラベル・件数で添える（§3.6 の `fail_counts` から）。
何も来ない日と配信が壊れている日を区別できるようにするため。

候補0件の日に関する読みやすさの規約が 2 つある。どちらも実物を見て決めた。

- **E1 の注記行を出さない。** 母集団も 0 なので「母集団 0 件のため未適用」は計算としては
  正しいが、適用する対象がそもそも無い日にこれを出すと E1 が壊れているように読める
- **落ちた条件の件数には「延べ件数」と明記する。** 1 銘柄が複数の条件で落ちるため合計は
  評価銘柄数を超える（2026-09-03 は 1,326 銘柄に対して延べ 9,000 件超）。
  一語添えないと数字が矛盾しているように見える

本文は 4,900 文字以内（Worker 側の上限）。超える場合は末尾のカードから落とし、
何件省いたかを本文に書く。見出しと免責は必ず残す。

### 4.3 配信内容と台帳の一致

**本文の入力は `delivered_*.csv` と `screen_summary_*.json` だけ。** 株価も指標も
配信時に計算し直さない。カードに出る値はすべて配信記録の列を整形しただけのものにする。

これを `tests/test_notify.py` で固定する（CSV に書いて読み直しても本文が変わらないこと、
必要な項目がすべて本文に現れること）。配信を見て気になった銘柄は、同じ日の
`delivered_*.csv` を引けば同じ数字が出る。

### 4.4 配信が失敗しても記録は失わない

ワークフローでは配信ステップを**コミットより後ろ**に置く。screen と resolve の結果は
配信を試みる前に main へ push 済みなので、Worker が落ちていても記録は残る。

配信の失敗は握り潰さない（ステップを赤にする）。握り潰すと、配信されない原因が
分からなくなる（CLAUDE.md の落とし穴）。

**テキストに落ちた日は本文の先頭に「画像生成に失敗（テキストで配信）」を入れる。**
通常はテキストが届かないので、届いた時点で異常である。受け取った側がすぐ分かるように
する。`WORKER_URL` 未設定（ローカル・DRYRUN）は失敗ではないので、テキストには落とさない。

### 4.5 画像カードの描画

`render/` に置く。**入力は `delivered_*.csv` と `screen_summary_*.json` だけ**（§4.3）。

| ファイル | 役割 |
| --- | --- |
| `render/context.py` | 記録から表示に必要な値だけを組み立てる純粋関数。整形はすべてここに閉じる |
| `render/template.html` | Jinja2。`#page1`（詳細）と `#page2`（サマリー）を持つ 1 枚の HTML |
| `render/render.py` | HTML にして Playwright で要素ごとに PNG 化 |

**1枚目（詳細）**

- ヘッダ: 日付・判定日・地合いゲージ（6点）・候補件数。E1 スキップ日はその旨（候補0件の日は出さない、§4.2）
- データの状況: 取得成功率・判定対象数・決算発表予定日が取れた銘柄数と割合、および
  **「決算日が取れない銘柄は、決算前でも候補に出ます。」**（A4 のカバー率が低い日でも
  読み手が誤解しないよう固定で出す、§2.6）
- 銘柄カード: 銘柄コード・銘柄名・33業種と**その5日順位**（例「銀行業 3/33位」、§2.9）・
  状態・連続点灯（2日目以降）／終値と止まった線と距離／
  **撤退ライン**（押し安値）と終値からの乖離率／**目標の目安**（直近高値）と乖離率／
  深さと押し目日数／20日平均売買代金／決算までの日数（未取得は赤字）／
  **出口ルール「押し安値割れで撤退／5日線回復で手仕舞い」を各カードに固定表示**
- 候補0件の日: 銘柄カードを出さず、落ちた条件の上位3つと延べ件数だけ
- フッタ: 順位ではないこと・免責

**2枚目（サマリー）**: 日付・地合い・候補件数と、銘柄コードと銘柄名の一覧だけ。詳細は1枚目を参照。

### 落とし穴: 手動実行（workflow_dispatch）は引け直後になりやすい

2026-08-31 に `data-daily` を手動実行したときに実際に起きたこと。

- **判定日がずれる。** ジョブは 15:29 JST に開始したが、`Daily data` ステップに入ったのは
  setup・install・テスト（約 1 分）を経た **15:30:52 JST**。`MARKET_CLOSE_HHMM`（15:30）を
  52 秒過ぎていたため当日足が確定扱いで残り、判定日は前営業日ではなく当日になった。
  手動実行の時刻から判定日を読むときは、**ジョブ開始時刻ではなく `Daily data` ステップの
  開始時刻**で考える（テストの所要時間だけ後ろにずれる）
- **引け直後の終値は暫定のことがある。** 引けの 52 秒後に取得した値が後で書き換わりうる。
  翌営業日の取得で `upsert` が改訂として検出し `store/revisions.csv.gz` に残るので store は
  自己修復するが、`daily/YYYY-MM-DD.csv.gz`（その時点で観測した足の記録）は最初に観測した
  値のまま残る。これは前向き検証の archive の設計どおりの挙動であって不具合ではない
- **判定日が翌営業日の実行と重複する。** 7:00 JST の実行は当日足がまだ無いので判定日が
  前営業日になる。引け後に手動実行すると同じ判定日の配信記録が 2 つでき、台帳で二重に
  数えられる。2026-08-31 はこれが起きたため、手動実行ぶんの `delivered_` と
  `screen_summary_` を削除して確定値ベースのスケジュール実行を正とした

**引け後に手動実行するなら、同じ判定日の記録が翌朝もう一度作られることを前提に、
どちらを残すか先に決めておく。** 引け前（15:30 JST より前に `Daily data` が始まる）なら
判定日は前営業日になるので重複しない。

### D-3（2026-09-04 決定・10日目より前）D-1 の観測日を判定日で数える

**D-1 の「10 営業日分」は、`screen_summary_*.json` の判定日（`asof`）のユニーク数で
数える。** ファイル数でも配信日でもない。同じ判定日の要約が複数ある場合は、配信日が
最も新しいものを採る。実装は `screen.observation_days()`、`screen` のログに毎日出す。

制定時（D-1）の「ファイルを日付順に 10 件読む」は、1 ファイル = 1 営業日を前提に
していた。§3.2 でファイル名に判定日を入れたことでこの前提が崩れ、3 通りの数え方が
現に食い違っている。

| 単位 | 2026-09-04 時点 |
| --- | --- |
| ファイル数 | 3 |
| 配信日ユニーク | 3 |
| **判定日ユニーク（採用）** | **2**（08-31, 09-03） |

**判定日を採る理由**: D-1 が測りたいのは「E1 の母集団が 10 件未満になる市場日が
どれだけあるか」であって、実行回数ではない。`screen_summary_2026-09-03_asof2026-09-03.json`
（09-03 引け後の手動実行）と `screen_summary_2026-09-04_asof2026-09-03.json`
（09-04 朝の定期実行）は**同じ市場日 09-03 を判定したもの**で、全項目が一致する。
これを 2 日と数えると同じ 1 日を二重に数えることになり、10 日目が実際より早く来る。

逆に、同じ配信日に判定日の違う 2 つがある日（引け前と引け後）は、別々の市場日を
判定しているので 2 日と数える。配信日で数えるとこれが 1 日に潰れる。

**観測できていない市場日は数えない（埋めない）。** 現時点の欠測は 2 つ:

| 判定日 | 何が起きたか |
| --- | --- |
| 2026-09-01 | 09-02 の実行が tz 不一致でクラッシュ（§6） |
| 2026-09-02 | 09-03 朝の要約が引け後の実行に上書きされた（§3.2） |

どちらもログには数字が残っているが、手で書き戻すと観測値と復元値が区別できなくなる。
10 日目は実測が 10 判定日に達した時点であり、暦の 10 営業日後ではない。

**この規則は 10 日目の数字を見る前に確定した。** 現時点で観測は 2 日、E1 スキップは
2 日（100%）だが、判定はしない。D-1 のとおり 10 日揃った時点で 1 回だけ行う。

### D-2（2026-08-31 決定・実行前）条件と閾値を動かさない期間

**記録（`outcome_*.csv` が付いた配信）が 20〜30 件貯まるまで、D-1 以外の条件と閾値は
変更しない。** 候補ゼロの日が続いても緩めない。

理由: 緩めた日と緩めない日が混ざると、線ごとの勝率も条件別の効き方も後から読めなくなる。

**候補ゼロが続いたときの読み方**（§3.6 の `fail_counts` を見る）:

  「今そういう相場ではない」ということなので、**対処は緩めることではなく待つこと**になる

どちらの場合も、この節に書いていない限り閾値は動かさない。
