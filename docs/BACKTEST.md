## 0. 引き継がないもの

`docs/DESIGN.md`・`docs/CLOSING.md` の**検定数・停止規則・撤退基準は引き継がない**
（CLAUDE.md）。前プロジェクト（v8 順張り押し目）は探索窓で 174 検定を積んでいるが、
**パターン検出には未使用であり、別仮説として検定は引き継がない**（設計責任者）。

同じ理由で、確認窓（2017-03〜2021-07）が前プロジェクトの頑健性窓と重なることも
引き継がない —— あちらは押し目型の仮説を見ており、パターン検出は別の仮説である。

引き継ぐのは**実装だけ**である。

### 2.1 ユニバース（2026-09-11 確定・以後動かさない）

**運用の `cli pattern` と同じ母集団にする。** 並び順は配信のために決めるものなので、
**配信に出ない銘柄の成績で決めては使えない**（設計責任者）。

T 時点で次をすべて満たす上場株式:

| ゲート | 値 | 出どころ |
| --- | --- | --- |
| 履歴 | **250 本以上** | `Settings.min_history_bars` |
| 20 日平均売買代金 | **2 億円以上** | `Settings.min_adv_jpy` |
| 終値 | **200 円以上** | `Settings.min_price` |

**数値をバックテスト側に書かない。`Settings` から受け取る** —— 書くと運用側と
黙ってずれる。ずれが再実行の原因になった（§7 Q-2）。

**当てないゲートが 2 つある。** 運用の `universe/build.py` にある**鮮度**（最終足が
7 日以内）と**分割疑い**は当てない。どちらも「いま取得できているか」を見るデータ品質の
ゲートで、過去の各 T について当時の状態を復元できない。流動性のゲートとは性質が違う。

**この母集団は今回限りの変更で、以後は動かさない**（設計責任者・§8 D-5）。

#### 指示された「3 億円」との差（2026-09-11）

設計責任者の指示は「20 日平均売買代金 3 億円以上」だったが、**運用の実際の下限は
2 億円**である（`Settings.min_adv_jpy` の既定 `2e8`。2026-09-10 の実行ログも
`min_adv=200000000`）。指示が挙げていた **1,277 銘柄という数字は 2 億円のゲートで
出たもの**なので、「運用と母集団を揃える」という指示の目的に沿うのは 2 億円である。
**2 億円を採った。** 3 億円にすると運用より狭い別の母集団になる。

## 3. ラベル

| 量 | 定義 |
| --- | --- |
| エントリー | `Open[T+1]` |
| 評価窓 | `T+1..T+20`（`PATTERN.md` §3.4 と同じ 20 本） |
| **超過リターン `r_20`** | `ln(Close[T+20] / Open[T+1])` − ユニバース等加重の同じ量 |
| `broke_stop` | 撤退の目安（パターンの最安値）を割ったか（`Low < pattern_low`） |
| `reached_target` | 測定目標に届いたか（`High > target`） |
| `success` | **撤退を割る前に目標到達。同日に両方なら失敗**（保守的） |
| MFE / MAE | 窓内の最大上昇幅・最大下落幅を **ATR 単位でも** |

### 3.1 `b >= 1` の行は「最初から目標を超えている」

`b` = 抜け幅 ÷ 高さ なので、

```
b >= 1  ⟺  終値[T] − ネックライン >= 高さ  ⟺  終値[T] >= ネックライン + 高さ = 測定目標
```

**この行の `reached_target` は「届いた」ではなく「最初から届いていた」を数えている。**
エントリー（Open[T+1]）以降の高値が、T の終値より下にある目標を超えるだけだからである。
`success` も同様に、ほぼ 1 日目に成立する。

**判定には影響しない**（主指標は `r_20` で、`reached_target` と `success` は診断列。
D-2）。ただし**読み違えると危ない**ので、`already_at_target` 列を持ち、表にも
**「既に到達」の比率**を出す。この比率が高い群では、隣の「目標到達」は
到達率ではない。

なお **`b >= 1` の行は比率（`rr`）が欠損になる** —— 目標までの距離 `up_pct` が
0 以下になり、`measured_move` が比率を出さないため（`PATTERN.md` §2.3）。

ベンチマークは `labels.universe_benchmark_returns` をそのまま使う（T+1 の始値で
ユニバース全銘柄を等金額買い、T+h の終値まで保有した対数リターンの単純平均）。

**主指標は超過リターン `r_20`。** 勝率・成功率（`success`）・`reached_target` の
比率は**診断列として併記するが、判定には使わない**（設計責任者）。

## 4. 探索（検定 10 件）

| # | 検定 | 群 |
| --- | --- | --- |
| 1〜5 | **パターン別** | 5 種 |
| 6〜10 | **抜け幅 `b` の 5 分位別** | 5 群 |

各群について **平均 `r_20`・Newey-West t・件数**を出す。

### 4.1 「5 種」の読み方

7 パターンのうち、**上昇フラッグ（C3）と上昇ペナント（C4）を除いた 5 種**とする。

- ダブルボトム（R1）/ トリプルボトム（R2）/ 逆三尊（R3）
- 上昇三角（C1）/ 上昇ボックス（C2）

C3・C4 は**日足かつ k=3 では構造的に検出されない**ことが確定している
（`PATTERN.md` §2.2・D-10）。群として立てても件数が 0 になる。

**この読み方が違っていれば言ってほしい**（§7 Q-1）。

### 4.2 抜け幅 `b` の分位

`b` = 抜け幅 ÷ 高さ（`PATTERN.md` §2.3 の `breakout_h`）。

**分位点は探索窓の全成立行から作り、確認窓にはその境界をそのまま当てる。**
確認窓で切り直すと、分位の意味が窓ごとに変わって再現を見られない。

**境界は `data/reference/pattern_quantile_edges.json` に確定値として置いてある**
（探索窓 2 回目・run 34623601516・43,550 行から作成）。

| 群 | `b` の範囲 |
| --- | --- |
| **Q1** | 下限 〜 **0.100000000000** |
| Q2 | 0.100000000000 〜 0.243011954106 |
| Q3 | 0.243011954106 〜 0.474567183169 |
| Q4 | 0.474567183169 〜 0.957142240563 |
| Q5 | 0.957142240563 〜 上限 |

**リポジトリに置いた理由**: Actions の cache は窓ごとに分かれていて期限もあるので、
確認窓の実行時に探索窓の出力が復元される保証が無い。**無いまま走らせると黙って
確認窓で切り直してしまう**（実装時に見つけた。`cli pattern-report` は確定値が
無ければ、探索窓以外では抜け幅の表を出さずに止まる）。

### 4.3 Newey-West の当て方

**イベントごとの値ではなく、日次平均の系列に当てる。** 評価窓が 20 本で重なるので、
イベントを独立と扱うと t 値が過大になる。

1. 各評価日について、その日に成立した行の `r_20` の平均を取る（**その群の行が
   0 件の日は系列に入れない。0 で埋めない**）
2. その日次系列に `newey_west_mean_t(x, lag=20)` を当てる

ラグは保有日数と同じ 20 本。`layer1.py` が日次 IC 系列に `lag=h` を当てているのと
同じ流儀である。

- 探索窓の t = 2.20 は、**10 検定のうち 1 つが通ったもの**であり、別の標本では通らな

  で、**両窓とも 2 に届いていない**。どのパターンが優れているという証拠は得られていない
- **全体の平均超過リターンは探索窓 +0.37%、確認窓 +0.05%（t = −0.38）。**
  パターン成立そのものに安定した優位は見えない ——「一番重いのはこれ」（設計責任者）
- 配信は続けてよい。**条件を満たす銘柄の一覧としては機能する。**「上がりやすい順」に
  並べる根拠が無い、というのが今回の結論である
- 記録は貯め続ける。**2026-10 末に実運用の 20 件が揃えば、バックテストとは別の標本**
  になる

**見直しは 1 回のみ。**

### Q-2（2026-09-11 提起・2026-09-11 クローズ）バックテストのユニバースが運用と違う

**§2 はユニバースを定義していなかった。** 実装は `replay.py` の
`replay_universe_tickers`（前プロジェクトから引き継いだ再生専用の定義）を使った。

| | 定義 | 2026-09-11 実測 |
| --- | --- | --- |
| **バックテスト** | 上場株式のうち **T 時点で履歴 250 本以上**。それだけ | 約 **3,640 銘柄** |
| **運用（`cli pattern`）** | 上記に加えて**売買代金 3 億円以上・株価 200 円以上**などのゲート | **1,277 銘柄**（2026-09-10） |

**測っている母集団が約 2.9 倍違う。** 1 日あたりの成立数も、バックテストが
**179.6 件/3,640 銘柄**（1 銘柄あたり約 4.9%）、運用が **13 件/1,277 銘柄**

9〜459 件）の範囲かもしれないが、**母集団が違うこと自体は確かである。**

どちらが正しいかは決めていない。選択肢:

- **(a) このまま**（履歴だけ）。前プロジェクトの再生と揃うが、**配信に出ない銘柄の
  成績で並び順を決める**ことになる
- **(b) 運用のゲートを入れる**。配信の母集団と揃うが、再生を全部やり直す（約 3 時間）

**並び順は配信のために決めるもの**（§ 目的）なので (b) が筋に見えるが、**窓を決めた
あとに母集団を変えるのは判定基準の変更にあたる**（§5「判定基準を結果を見てから
変えない」）。こちらでは決めない。

### 10.2 B. ATR×2 を出口とした場合の成績（検定 1 件）

**事前登録（結果を見る前に固定）:**
