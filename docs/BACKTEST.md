# BACKTEST.md — パターン検出のバックテスト（仕様）

**目的は 1 つだけ。配信の並び順を決める根拠を得る**（2026-09-11・設計責任者）。
探索対象は 2 つ、検定は 10 件。それ以上に広げない。

現在の並び順は**売買代金の降順**である（`docs/PATTERN.md` §6）。**再現しなければ
これを変えない。** 「何か効くものを探す」ための調査ではない。

この文書が正の情報源である。ここに書いていない判断が必要になったら、実装せず
§7 の質問ログに追記して止まる（CLAUDE.md）。

## 0. 引き継がないもの

`docs/DESIGN.md`・`docs/CLOSING.md` の**検定数・停止規則・撤退基準は引き継がない**
（CLAUDE.md）。前プロジェクト（v8 順張り押し目）は探索窓で 174 検定を積んでいるが、
**パターン検出には未使用であり、別仮説として検定は引き継がない**（設計責任者）。

同じ理由で、確認窓（2017-03〜2021-07）が前プロジェクトの頑健性窓と重なることも
引き継がない —— あちらは押し目型の仮説を見ており、パターン検出は別の仮説である。

引き継ぐのは**実装だけ**である。

| 引き継ぐ | どこ |
| --- | --- |
| 再生の骨組み（日別に T を回して保存） | `validation/replay.py` |
| ユニバース等加重ベンチマーク・超過リターン | `validation/labels.py` |
| Newey-West の平均・t 値 | `validation/layer1.py` の `newey_west_mean_t` |
| ホールドアウトの物理的な打ち切り | `validation/replay.py` の `_truncate_before_holdout` |
| ルックアヘッド検査 | `tests/test_lookahead.py` のハーネス |

## 1. 窓

| 窓 | 期間 | 用途 |
| --- | --- | --- |
| **探索** | 2021-08-01 〜 2026-01-30 | パターン別・抜け幅別の成績 |
| **確認** | 2017-03-15 〜 2021-07-31 | 探索結果の再現確認 |
| **ホールドアウト** | 2026-02-01 〜 2026-08-01 | **最終 1 回。確認窓を通過するまで触らない** |

**ホールドアウトは明示フラグ無しに生成しない**（CLAUDE.md の絶対規則）。
`replay.py` と同じく、OHLCV 自体をホールドアウト開始日より前で物理的に打ち切る
—— 日付で T を絞るだけでは、窓の端の T が T+20 でホールドアウト側のバーを読む。

探索窓は既存の `MAIN_WINDOW` と同じ、ホールドアウトは既存の `HOLDOUT_WINDOW` と
同じ。確認窓だけが新しい。

## 2. 検出

**`cli pattern` と同じ判定をそのまま載せる**（`features/pattern.py`）。
**判定式・閾値は変更しない** —— ±1.5%・±0.75%・22 日・63 日・ε・旗竿・15 日は
`docs/PATTERN.md` §1 の事前登録値のままである。

各評価日 T で**成立した行を全件記録する**（監視は記録しない。成立が事象、監視が
状態という §3.1 の区別はここでも同じ）。

記録する列: 銘柄・パターン名・ネックライン・抜け幅・比率・撤退・目標・span・
上辺の散らばり・売買代金・33業種（`PATTERN.md` §3.3 の配信記録と同じ列）。

**業種・売買代金・span・散らばりは記録するが探索しない**（§5 の禁止事項）。

## 3. ラベル

| 量 | 定義 |
| --- | --- |
| エントリー | `Open[T+1]` |
| 評価窓 | `T+1..T+20`（`PATTERN.md` §3.4 と同じ 20 本） |
| **超過リターン `r_20`** | `ln(Close[T+20] / Open[T+1])` − ユニバース等加重の同じ量 |
| `broke_stop` | 撤退の目安（パターンの最安値）を割ったか（`Low < pattern_low`） |
| `reached_target` | 測定目標に届いたか（`High > target`） |
| `success` | **撤退を割る前に目標到達。同日に両方なら失敗**（保守的） |
| MFE / MAE | 窓内の最大上昇幅・最大下落幅を **ATR 単位でも** |

ベンチマークは `labels.universe_benchmark_returns` をそのまま使う（T+1 の始値で
ユニバース全銘柄を等金額買い、T+h の終値まで保有した対数リターンの単純平均）。

**主指標は超過リターン `r_20`。** 勝率・成功率（`success`）・`reached_target` の
比率は**診断列として併記するが、判定には使わない**（設計責任者）。

## 4. 探索（検定 10 件）

| # | 検定 | 群 |
| --- | --- | --- |
| 1〜5 | **パターン別** | 5 種 |
| 6〜10 | **抜け幅 `b` の 5 分位別** | 5 群 |

各群について **平均 `r_20`・Newey-West t・件数**を出す。

### 4.1 「5 種」の読み方

7 パターンのうち、**上昇フラッグ（C3）と上昇ペナント（C4）を除いた 5 種**とする。

- ダブルボトム（R1）/ トリプルボトム（R2）/ 逆三尊（R3）
- 上昇三角（C1）/ 上昇ボックス（C2）

C3・C4 は**日足かつ k=3 では構造的に検出されない**ことが確定している
（`PATTERN.md` §2.2・D-10）。群として立てても件数が 0 になる。

**この読み方が違っていれば言ってほしい**（§7 Q-1）。

### 4.2 抜け幅 `b` の分位

`b` = 抜け幅 ÷ 高さ（`PATTERN.md` §2.3 の `breakout_h`）。

**分位点は探索窓の全成立行から作り、確認窓にはその境界をそのまま当てる。**
確認窓で切り直すと、分位の意味が窓ごとに変わって再現を見られない。

### 4.3 Newey-West の当て方

**イベントごとの値ではなく、日次平均の系列に当てる。** 評価窓が 20 本で重なるので、
イベントを独立と扱うと t 値が過大になる。

1. 各評価日について、その日に成立した行の `r_20` の平均を取る（**その群の行が
   0 件の日は系列に入れない。0 で埋めない**）
2. その日次系列に `newey_west_mean_t(x, lag=20)` を当てる

ラグは保有日数と同じ 20 本。`layer1.py` が日次 IC 系列に `lag=h` を当てているのと
同じ流儀である。

## 5. 判定

**先に決める。結果を見てから変えない。**

| 段 | 基準 |
| --- | --- |
| 探索窓 | **全体平均を上回り、かつ NW t ≥ 2** のものを候補とする |
| 確認窓 | 候補が**再現**（符号が正、かつ t ≥ 2）すれば**採用** |
| 再現しない | **終了。並び順は売買代金のまま** |
| ホールドアウト | **採用が決まった後に 1 回のみ** |

**見直しは 1 回のみ。**

### 禁止事項（設計責任者・2026-09-11）

- **探索対象を 10 件から増やさない。** 業種・売買代金・span・散らばり・連続日数・
  地合いは**探索しない**（記録はする）
- **判定基準を結果を見てから変えない**
- **見直しは 1 回のみ**
- **確認窓を通過するまでホールドアウトに触れない**
- **判定式・閾値を変更しない**（±1.5%・±0.75%・22 日・63 日・ε・旗竿・15 日）

## 6. 報告

**探索窓の結果が出たら、確認窓に進む前に報告する。**

出すのは**表のみ。数値の解釈も採否の判断もしない**（CLAUDE.md「検証結果を解釈
しない」）。表には必ず**件数（母数）**を併記する。

| 表 | 列 |
| --- | --- |
| パターン別 | パターン・件数・平均 `r_20`・NW t・（診断）勝率・成功率・MFE/MAE 中央 |
| 抜け幅分位別 | 分位・`b` の範囲・件数・平均 `r_20`・NW t・（診断）同上 |
| 全体 | 件数・平均 `r_20`・NW t・評価日数・カバーした期間 |

**ユニバースの定義も併記する**（§7 Q-2）。運用の `cli pattern` とは母集団が違う。

**データのカバー範囲も必ず報告する。** store の履歴が確認窓の開始日まで届いて
いない可能性がある（backfill は 2600 本）。届いていなければ、**実際に評価できた
期間をそのまま書く** —— 窓の定義を黙って縮めない。

## 7. 質問ログ

### Q-1（2026-09-11 提起・2026-09-11 クローズ）「パターン別（5 種）」の 5 つ

7 パターンのうちどの 5 つかが明示されていない。**C3・C4 を除いた 5 種**と読んで
実装した（§4.1）。C3・C4 は日足かつ k=3 では構造的に検出されないことが確定して
いる（`PATTERN.md` D-10）ので、群として立てても 0 件になるため。

**回答（設計責任者・2026-09-11）: R1/R2/R3/C1/C2 で正しい。** C3・C4 は構造的に
0 件なので群として立てても空になる。**検定は 10 件のまま変わらない。**

### Q-2（2026-09-11 提起・未クローズ）バックテストのユニバースが運用と違う

**§2 はユニバースを定義していなかった。** 実装は `replay.py` の
`replay_universe_tickers`（前プロジェクトから引き継いだ再生専用の定義）を使った。

| | 定義 | 2026-09-11 実測 |
| --- | --- | --- |
| **バックテスト** | 上場株式のうち **T 時点で履歴 250 本以上**。それだけ | 約 **3,640 銘柄** |
| **運用（`cli pattern`）** | 上記に加えて**売買代金 3 億円以上・株価 200 円以上**などのゲート | **1,277 銘柄**（2026-09-10） |

**測っている母集団が約 2.9 倍違う。** 1 日あたりの成立数も、バックテストが
**179.6 件/3,640 銘柄**（1 銘柄あたり約 4.9%）、運用が **13 件/1,277 銘柄**
（約 1.0%）だった。運用の 13 件は 1 日ぶんなので日々のばらつき（バックテストでは
9〜459 件）の範囲かもしれないが、**母集団が違うこと自体は確かである。**

どちらが正しいかは決めていない。選択肢:

- **(a) このまま**（履歴だけ）。前プロジェクトの再生と揃うが、**配信に出ない銘柄の
  成績で並び順を決める**ことになる
- **(b) 運用のゲートを入れる**。配信の母集団と揃うが、再生を全部やり直す（約 3 時間）

**並び順は配信のために決めるもの**（§ 目的）なので (b) が筋に見えるが、**窓を決めた
あとに母集団を変えるのは判定基準の変更にあたる**（§5「判定基準を結果を見てから
変えない」）。こちらでは決めない。

**確認窓には進んでいない。** ここで止まる。

## 8. 決定ログ

### D-1（2026-09-11）探索対象は 2 つ・検定は 10 件

パターン別（5 種）と抜け幅 `b` の 5 分位のみ。**業種・売買代金・span・散らばり・
連続日数・地合いは探索しない。** 記録はするが検定しない。

前プロジェクトは 174 検定を積んで撤退した（`docs/CLOSING.md`）。**同じ形にしない**
ために、探索対象を先に 2 つへ絞ってから始める。

### D-2（2026-09-11）主指標は超過リターン。勝率と成功率は診断

`r_20` で判定する。勝率・`success`・`reached_target` の比率は表に併記するが、
**判定には使わない**（設計責任者）。

### D-3（2026-09-11）分位の境界は探索窓で作り、確認窓に当てる

確認窓で切り直すと分位の意味が窓ごとに変わり、再現を見たことにならない。

### D-4（2026-09-11）Newey-West は日次平均系列に当てる

イベント単位だと評価窓 20 本の重なりで t 値が過大になる。群の行が 0 件の日は系列に
入れない（0 で埋めない）。ラグは保有日数と同じ 20。
